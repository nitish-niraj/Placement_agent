1. Executive Summary
Placement Intelligence Agent (PIA) is a private, personal AI agent that continuously processes selected WhatsApp group conversations, especially placement and academic groups, and turns noisy chat streams into personally relevant, persistent knowledge. It must detect company eligibility lists in Excel, CSV, PDF, image, or screenshot form; identify the user using name and other identity signals; remember company-specific eligibility; connect later messages to that remembered context; extract deadlines and placement events; suppress repeated notifications; and surface important academic or administrative information even when it is not placement-related.
The system is explicitly designed as a hybrid deterministic + AI platform. Code must own identity, timestamps, persistence, state transitions, permissions, notification history, and safety controls. AI models may interpret language, classify information, extract entities, understand messy documents, and perform semantic matching, but model output must be validated before it changes authoritative state.
[TABLE]
Primary outcome The user should not need to read the placement group continuously. The system should behave as a reliable personal information filter: “Tell me what matters to me, remember the context, and do not make me read the same thing twice.”
[/TABLE]
2. Product Goals and Non-Goals
2.1 Goals
Capture messages and media from selected WhatsApp groups through a dedicated connector layer.
Understand message intent and classify domain: placement, academic, examination, administrative, event, or general.
Detect eligible-candidate announcements and analyze attached Excel/PDF/image/screenshot lists.
Match the personal candidate profile with exact, normalized, variant, roll-number, and controlled fuzzy matching.
Persist company eligibility and build a company/application lifecycle memory.
Extract deadlines, exam dates, interview schedules, links, forms, KYC sessions, venues, and required actions.
Detect repeated or semantically duplicate information and notify only on genuinely new information.
Provide a concise, evidence-backed notification and an auditable dashboard/history.
Later support human-approved actions such as preparing forms or KYC submissions without allowing uncontrolled autonomous submission by default.
2.2 Non-goals for MVP
Autonomous form submission or irreversible external actions.
Processing every personal WhatsApp conversation by default.
Publishing or sharing group content with third parties.
Using an LLM as the sole source of truth for candidate identity or eligibility.
Building a general-purpose autonomous browsing agent before the core information pipeline is reliable.

4. Product Principles
Personal relevance over volume: the system should optimize for “what matters to me”, not “summarize everything”.
Persistent memory over isolated prompts: company and event context must survive individual model calls.
Evidence over confidence theater: important outputs must include source references and extraction/match reasoning.
Deterministic controls over model improvisation: safety, state, deduplication, and permissions are code-owned.
Incremental implementation: every phase must be independently testable and deployable.
Human approval for irreversible actions: autonomous actions are disabled by default.
Provider independence: WhatsApp connectivity must be replaceable through an adapter boundary.

7. Functional Requirements
7.1 WhatsApp Connection & Group Registry
FR-WA-001 — Connect WhatsApp account through Evolution API instance.  [MUST]
User can pair and see connection state; reconnect failures are surfaced.
Acceptance: Connection state transitions are persisted and visible.
FR-WA-002 — Receive group messages as normalized internal events.  [MUST]
Provider payload becomes a stable internal message schema.
Acceptance: Same provider event reprocessed twice creates one logical message.
FR-WA-003 — Persist group metadata.  [MUST]
Group ID, name, participant metadata available where provider supplies it.
Acceptance: Group registry can identify a message source.
FR-WA-004 — Allow group allowlist/denylist.  [MUST]
Only selected groups are processed by default.
Acceptance: Unselected groups are not sent to AI pipeline.
FR-WA-005 — Classify groups into Placement/Academic/Administrative/General/Other.  [SHOULD]
Manual override is supported.
Acceptance: Classification can be edited without modifying raw messages.
FR-WA-006 — Receive message attachments/media metadata and fetch content when permitted.  [MUST]
Documents/images are available to media processor.
Acceptance: Failed media downloads become retryable jobs, not silent drops.
7.2 Message Normalization & Idempotency
FR-MSG-001 — Normalize message IDs, sender, group, timestamp, text and media references.  [MUST]
Canonical schema independent of provider-specific payload.
Acceptance: Unit tests cover missing/optional provider fields.
FR-MSG-002 — Apply idempotent ingestion.  [MUST]
Duplicate webhook/event does not create duplicate record or duplicate job.
Acceptance: 10 identical deliveries result in one stored logical event.
FR-MSG-003 — Preserve raw provider payload securely for audit/debugging with retention policy.  [SHOULD]
Raw data can be linked to normalized message.
Acceptance: Retention is configurable.
FR-MSG-004 — Track processing states.  [MUST]
RECEIVED, QUEUED, PROCESSING, PROCESSED, FAILED, RETRYING.
Acceptance: State transitions are queryable.
7.3 Message Classification
FR-CLS-001 — Classify domain: PLACEMENT, ACADEMIC, EXAMINATION, ADMINISTRATIVE, EVENT, GENERAL, UNKNOWN.  [MUST]
Every eligible message gets a domain label plus confidence/evidence.
Acceptance: Low-confidence cases are not silently treated as high importance.
FR-CLS-002 — Classify importance: CRITICAL, HIGH, MEDIUM, LOW, IGNORE.  [MUST]
Importance is separate from domain.
Acceptance: A non-placement academic deadline can be CRITICAL.
FR-CLS-003 — Extract company names, institutions, dates, links, locations, actions, deadlines and document references.  [MUST]
Output follows structured schema.
Acceptance: Unknown fields are null, not hallucinated.
FR-CLS-004 — Support rule-based overrides for known patterns.  [SHOULD]
User/system rules can override model classification.
Acceptance: Overrides are auditable.
7.4 Candidate Profile & Personal Knowledge
FR-PRO-001 — Create secure candidate profile.  [MUST]
Stores user-entered identity and eligibility attributes.
Acceptance: Profile changes are audited.
FR-PRO-002 — Support identity aliases and identifiers.  [MUST]
Name variants, roll number, registration number, student ID and approved aliases.
Acceptance: Matcher can use configured identifiers.
FR-PRO-003 — Support profile documents.  [SHOULD]
Resume, certificates and academic proofs can be attached.
Acceptance: Documents have explicit access permissions.
FR-PRO-004 — Allow user to correct a false match or false negative.  [MUST]
Correction becomes supervised feedback.
Acceptance: Correction is stored with timestamp and source.
7.5 Eligibility List Intelligence
FR-ELG-001 — Detect that a message/attachment represents an eligible-candidate list.  [MUST]
Recognizes text, file name and document content signals.
Acceptance: Tested on text-only, file-only and combined announcements.
FR-ELG-002 — Parse XLSX/XLS/CSV lists.  [MUST]
Extract rows/columns and likely identity fields.
Acceptance: Common header variations are supported.
FR-ELG-003 — Parse PDFs.  [MUST]
Extract text and preserve page/position evidence where feasible.
Acceptance: User match includes page reference.
FR-ELG-004 — Analyze images/screenshots.  [MUST]
OCR first; vision model used when OCR is insufficient.
Acceptance: Match includes image/page evidence.
FR-ELG-005 — Normalize candidate names before matching.  [MUST]
Case, whitespace, punctuation, Unicode and common formatting variations normalized.
Acceptance: Exact normalized matches work reliably.
FR-ELG-006 — Use multiple identity signals.  [MUST]
Prefer roll/registration ID when available; use name as primary/secondary depending on data.
Acceptance: Ambiguous same-name cases are not auto-confirmed.
FR-ELG-007 — Support controlled fuzzy matching.  [SHOULD]
Fuzzy match is used only after deterministic checks and must return confidence plus evidence.
Acceptance: Configurable threshold; ambiguous matches require review.
FR-ELG-008 — Create Eligibility Record when the user is found.  [MUST]
Company + candidate + source + confidence + detected_at persisted.
Acceptance: Record is linked to original message/document.
FR-ELG-009 — Create Not Found / Unknown state without claiming ineligibility.  [MUST]
Absence from one document is not interpreted as definitive rejection unless document semantics support it.
Acceptance: System distinguishes NOT_FOUND from NOT_ELIGIBLE.
7.6 Company Memory & Lifecycle
FR-MEM-001 — Create company entity from messages.  [MUST]
Canonical company name plus aliases.
Acceptance: Accenture/Accenture India style variants can map to one entity when evidence supports it.
FR-MEM-002 — Persist company-specific eligibility state.  [MUST]
ELIGIBLE, NOT_ELIGIBLE, UNKNOWN, EXPIRED, SUPERSEDED.
Acceptance: State changes keep source evidence.
FR-MEM-003 — Associate later messages with known companies.  [MUST]
Company mention, aliases, event context and group context used.
Acceptance: “Accenture OA” resolves to existing company record.
FR-MEM-004 — Track application lifecycle.  [SHOULD]
DISCOVERED → ELIGIBLE → REGISTRATION → OA → SHORTLISTED → INTERVIEW → SELECTED/REJECTED.
Acceptance: Transitions are event-driven and reversible via correction.
FR-MEM-005 — Support company-specific watch state.  [MUST]
Once user is eligible, future related messages are prioritized automatically.
Acceptance: No manual re-subscription needed.
7.7 Event & Deadline Engine
FR-EVT-001 — Extract event types.  [MUST]
REGISTRATION, FORM, KYC, OA, EXAM, INTERVIEW, SHORTLIST, RESULT, VENUE, DOCUMENT_SUBMISSION, JOINING, OTHER.
Acceptance: Structured event record created.
FR-EVT-002 — Extract absolute and relative dates/times.  [MUST]
“today 6 PM”, “tomorrow”, and explicit dates resolved using user timezone.
Acceptance: Stored timestamp includes timezone.
FR-EVT-003 — Track deadlines as first-class objects.  [MUST]
Deadline state is OPEN, DUE_SOON, EXPIRED, CANCELLED, COMPLETED.
Acceptance: Deadline can be updated by later message.
FR-EVT-004 — Detect event deltas.  [MUST]
New link, changed deadline, new venue, changed time etc. update existing event.
Acceptance: User is notified only for meaningful delta.
FR-EVT-005 — Prevent hallucinated deadlines.  [MUST]
Missing date/time remains unknown.
Acceptance: Model cannot invent a deadline.
7.8 Semantic Deduplication & Information Delta
FR-DED-001 — Detect exact duplicate messages.  [MUST]
Content hash plus provider ID.
Acceptance: Duplicate does not re-notify.
FR-DED-002 — Detect near-duplicate messages.  [MUST]
Normalized textual similarity.
Acceptance: Minor wording changes map to same candidate event when appropriate.
FR-DED-003 — Detect semantic duplicate announcements.  [MUST]
Compare event/company/action/deadline facts, not only raw text.
Acceptance: Three reminders about same deadline produce one canonical event.
FR-DED-004 — Detect information delta.  [MUST]
Same event with new link/venue/deadline/status is updated, not discarded.
Acceptance: New material information can trigger a notification.
FR-DED-005 — Maintain canonical event history.  [SHOULD]
Every update links to source messages.
Acceptance: Timeline shows original and updates.
7.9 Personal Relevance & Notification
FR-NOT-001 — Calculate personal relevance.  [MUST]
Uses profile, eligibility, company memory, academic context, role and actionability.
Acceptance: Relevant company update is prioritized.
FR-NOT-002 — Notify eligible-company updates.  [MUST]
Any new high-value event for a company where user is eligible is considered for immediate notification.
Acceptance: Accenture eligibility followed by OA deadline produces alert.
FR-NOT-003 — Notify critical academic/admin information.  [MUST]
Placement group can carry important non-placement information.
Acceptance: Academic exam deadline is surfaced even with no company relation.
FR-NOT-004 — Suppress already-delivered identical information.  [MUST]
Notification history prevents repeat alerts.
Acceptance: Repeated reminder does not spam user.
FR-NOT-005 — Support escalation.  [SHOULD]
Upcoming deadline becomes more urgent as due time approaches.
Acceptance: Configurable reminder windows.
FR-NOT-006 — Provide daily digest.  [SHOULD]
Summary groups urgent, placement, academic, and tracked items.
Acceptance: Digest contains only new/actionable information.
FR-NOT-007 — Include evidence in alerts.  [MUST]
Source group/message and attachment when relevant.
Acceptance: User can trace the alert to its origin.

14. Reliability & Observability
Every inbound message receives a correlation ID.
Every background job has a retry count, error class and last error.
AI requests log model/provider, latency, token/usage metadata where available, schema validation result, but not unnecessary sensitive content.
Core metrics: messages received, processing lag, attachment success rate, classifier confidence distribution, eligibility match rate, false-match corrections, duplicate suppression count, notifications sent, notification delivery failures, deadline reminders delivered on time.
Create a dead-letter queue for permanently failing jobs.
Provide an operational health endpoint for API, DB, queue, Evolution API connection and worker health.

Placement WhatsApp Assistant
Requirements & Phased Build Plan
Prepared for: Niraj  |  Version 1.0  |  August 2026
1. Project Summary
An AI agent that connects to your own WhatsApp account (via Evolution API) to read placement-related group chats, and delivers:
A clean, deduplicated summary of new messages
Automatic detection of company eligibility lists (text, Excel, or image-based) and a search for your name/roll number in them
Memory of which companies you are eligible for, with automatic high-priority alerts on any future related update
Separate flagging of important academic notices that aren't placement-related
(Future phase) Draft-filling of forms using your stored profile data, with you doing the final submit
2. Reality Check — Read This First
Before writing any code, it's worth being fully honest about what this tool actually is and its limits:
Evolution API connects via the Baileys library, which talks to WhatsApp using the WhatsApp Web protocol. This is an unofficial / reverse-engineered method, not Meta's sanctioned Business API for this kind of use.
It only works with your own WhatsApp account, linked the same way WhatsApp Web is (QR scan). It cannot access anyone else's private account or data you don't already have legitimate access to.
Because it's unofficial, WhatsApp's Terms of Service don't officially permit this style of automated client — there is a non-zero risk of the linked number being flagged or banned, especially with heavy or bulk activity.
Read-only monitoring (no sending, no spam) on a group you're already a genuine member of is the lowest-risk pattern, but not a zero-risk one.
Recommendation: link a secondary WhatsApp number to this project for at least the first few months, not your primary number used for job/company communication.
This is a personal automation tool for messages you already have legitimate access to as a group member — treat it accordingly, and keep the recommendation above in mind.
3. Architecture Overview
High-level data flow:
WhatsApp placement groups → Evolution API (self-hosted, Docker) → webhook fires on every new message
Backend service (Node.js or Python) receives the webhook and routes the message by type
Text messages → classification + summarization engine
Images → OCR / vision-LLM extraction
Excel/doc attachments → spreadsheet parser
Everything lands in PostgreSQL: messages, eligibility_lists, companies, user_profile, notification_log
A notification layer (Telegram bot recommended) pushes digests and alerts to you
4. Feature Breakdown — Phase by Phase
Phase 0 — Foundation (Week 1)
Goal: get raw messages flowing from the WhatsApp group into your own database.
☐  Set up Evolution API locally (Docker) or on a small VPS
☐  Connect a WhatsApp number (recommended: secondary number) via QR
☐  Identify and record the Group JIDs of your placement groups
☐  Configure a webhook so every new group message posts to your backend
☐  Backend: a simple endpoint that logs incoming messages (text, sender, timestamp, media type) into PostgreSQL
☐  Verify with a test message that it lands correctly in the database
Exit criteria: every message in your target groups (text + media metadata) is reliably captured and stored.
Phase 1 — Daily Summary (Week 2)
Goal: turn raw messages into a readable daily digest.
☐  Cron job pulls unsummarized messages on a schedule (e.g., every evening)
☐  Batch messages sent to an LLM (Claude API) with a summarization prompt
☐  Output a structured, date-wise and group-wise summary
☐  Deliver via a Telegram bot (simplest) or email
☐  Basic dedup: hash normalized message text, skip repeats seen recently in the same group
Exit criteria: you get one clean daily digest instead of scrolling through raw WhatsApp messages.
Phase 2 — Eligibility List Detection (Weeks 3-4)
Goal: automatically detect company eligibility lists and check your own name against them.
☐  Text-based lists: LLM classifies a message as an eligibility list using patterns (company name + "eligible" + names/roll numbers)
☐  Excel attachments: auto-download and parse with pandas/openpyxl, searching all sheets and columns with fuzzy name matching
☐  Image-based lists (screenshots of Excel/PDF): OCR or a vision-capable LLM extracts the text, then searches for your name
☐  Store the result as: company, eligible status, source message, list type, confidence
☐  Notification always states a confidence level and links back to the original message — never a silent, fully-confident claim from an image-only source
Exit criteria: for any eligibility list posted — text, Excel, or image — the agent correctly finds or flags your name, with visible confidence and a source reference.
Phase 3 — Company Memory & Smart Alerts (Week 5)
Goal: remember which companies you are eligible for, and connect future messages to that memory.
☐  A companies table storing name, eligibility status, first-seen date, and key dates
☐  New messages mentioning a company already in that table are tagged as relevant to you and prioritized or sent as an immediate alert if time-sensitive
☐  Deadline/date extraction from message text, with optional reminders ahead of the deadline
☐  Academic-but-not-placement messages get a separate tag so they're visible but not mixed into placement alerts
Exit criteria: once a company (e.g., Accenture) is marked eligible, any later message mentioning it is automatically flagged as high priority, without you repeating yourself.
Phase 4 — Robust Deduplication (ongoing, refine after Phase 1)
Goal: the same message forwarded five times in the group should reach you once.
☐  Content-hash dedup for exact or near-exact text
☐  Perceptual hashing (pHash) for images, so re-forwarded or re-compressed screenshots are still recognized
☐  Time-window logic: content reappearing after 7+ days is treated as a legitimate reminder, not noise
Phase 5 — Future / Advanced (only after Phases 0-4 are solid)
Goal: assist with forms and sessions using your stored profile data.
☐  A structured user_profile schema (name, roll no, CGPA, branch, contact, resume link, skills, projects) filled once by you
☐  Form auto-fill via browser automation (e.g., Playwright) matching form fields to your profile — feasible, but each company's form differs, so expect to review the first few closely
☐  KYC / identity-verification sessions: intentionally NOT automated (see note below)
☐  Realistic version: the agent pre-fills a form draft and reminds you of session timing; you perform the actual submit or attend the session
A KYC or verification session exists specifically to confirm it's really you. Automating attendance would misrepresent your identity to the company or college and is not something to build, regardless of convenience — this should stay a manual, human step.
